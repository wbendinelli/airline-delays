# data/derived/

Intermediates and on-demand aggregates of the flight table at grains other than
the committed `group x route x month` fact table -- route-day, route-week and
similar, produced by `aggregate()` in `src/airline_delays/fact/` (see
`DECISIONS.md` ADR-0004). Nothing here is a second source of truth: every table
is a tested, additive projection of the flight table, regenerated by running the
aggregation again, never hand-edited.

Git-ignored except for this README (see `.gitignore`): these tables exist only
as long as someone needs that particular grain locally.

## `ml/`

The flight-level modelling table of the prediction stage:
`data/derived/ml/year=YYYY/part-0.parquet`, one row per **scheduled** flight of
the replication universe (ADR-0002), 10,200,560 rows over 2000-2013, plus a
`manifest.json` with the per-year accounting. Built by `just predict-dataset`
in about 25 seconds, one DuckDB scan per staged year. Its 65 columns are
declared in `src/airline_delays/schema/columns.py` (layer `ml`), rendered in
`docs/dictionary.md` and described in `datapackage.json`; the table itself is
flight-level and stays out of git like the staged layer (ADR-0004).

## Intermediates of `just fact`

`node_day_hour.parquet` (movements per node, day and scheduled hour, the input
to the congestion proxy of ADR-0007) and `route_month_context.parquet`
(route-month counts outside the replication universe, plus the order statistics
a fact table cannot carry) are written by `just fact` and read by
`airline_delays.panel`. They are inputs `just check-analysis` needs to rebuild
the panel, not deliverables, and they are not part of the `ml` layer.

## `demo/`

`just demo` writes its staged, analysis and replication outputs under
`data/derived/demo/`; it never touches the committed tables.
